# Conventions

The rules that keep the parameters, the 3D models, the simulator and the tests consistent with each other. The page's design principles are in [ui-design.md](ui-design.md), how to run and release it in [development.md](development.md), and the licences in [licensing.md](licensing.md).

## Units and scale

| Where | Unit |
|---|---|
| `params/machine.json` | **millimetres** and **degrees**; the timing of a pick as fractions **φ** from 0 to 1 |
| Blender scenes | Internal unit is **metres** (unit scale 1.0), with the length display set to millimetres. Build scripts convert mm → m once, when creating geometry. |
| glTF / three.js | **metres** (glTF standard), so 1 three.js unit = 1 m |

Do not set Blender's unit scale to 0.001. The glTF exporter ignores it, and models come out 1000× too big.

Every value in `params/machine.json` is `{v, unit, conf, src, note}`: `conf` says how sure it is (`doc`, `drawing`, `derived`, `est`, `design`) and `src` names its source in [research/sources/bibliography.md](../research/sources/bibliography.md).

## Frames

- **The 2D section frame:** one cross-row of the head seen from the side. *x* runs along the needles, 0 at the needle board's face, positive toward the spring box (the card cylinder is on the −*x* side); *y* is up, 0 at the top of the bottom board.
- **The machine frame (the 3D models):** **X** across the loom, along the needles (the section's *x*, so the needle board's face is X = 0); **Y** from the front (the weaver, the cloth) to the back (the warp beam), as the 2D side view's *x*; **Z** up from the floor. A point (*x*, *y*) of the section is (*x*, `section_y`, `section_z` + *y*) in the machine frame (`params/machine.json`, `machine_frame`).
- **Blender is Z-up; glTF and three.js are Y-up.** The glTF exporter converts automatically ("+Y Up" on): a machine point (X, Y, Z) is three.js (X, Z, −Y) / 1000 (`js/scene/frame.js`). Never rotate by hand to compensate.

## The cards and the hooks

- **One convention, everywhere: hole = 1 = warp end lifted.** A blank pushes its needle, and the needle's eye pushes its hook off the knife, so the end stays down.
- **Hook h** (1-based) sits at card **column ⌈h/8⌉** and **row ((h − 1) mod 8) + 1**: a column per cross-row of the head, a row per needle tier, row 1 the top needle (`holeOfHook()` in `js/sim/deck.js`).
- **Pick p** (0-based) is woven from card p of the chain; a closed chain loops. The first card weaves the bottom row of the cloth.

## Parts, motions and naming

- **Every moving part is its own node,** driven by **one scalar** from the simulation. The node's glTF extras say how (`motion`), and `js/scene/rig.js` applies it:

  | `motion` | The scalar | Notes |
  |---|---|---|
  | `translate` | mm along `axis` | |
  | `rotate` | degrees about `axis`, through the node's origin | |
  | `reach` | mm the far end moves along `move` | A straight piece from a fixed end to a moving one, turned and stretched so it stays joined: the hook's bends, cords through the comber board, warp ends through the mails |
  | `stretch` | its length, mm | A spring along its local +Y |
  | `show` | 0 or 1 | |
  | `segment` | (two points) | A cord between two moving points, set from both |

- **Node names** use the form `<assembly>.<part>[.<index>]`, lower-case ASCII: `hooks.hook.0`, `needles.needle.3`, `griffe.knife.0`, `cylinder.prism`, `harness.mail.0.1`. They are the contract between the glTF and the web code, so changing one is an API change. three.js's GLTFLoader strips reserved characters (including `.`) from node names, so always look nodes up through `gltfName()` (`THREE.PropertyBinding.sanitizeNodeName`), and never give two parts names that collide once the dots are removed.
- **Anchors** (glTF extras, node-local points) mark what the acceptance checks measure, so the checks never re-derive the build.
- **Hierarchy** follows physical attachment: the prism is a child of the cylinder's batten, the hook's upper part a child of its lifting part.
- **Materials** are named by function (`steel_wire`, `iron`, `oak`, `card`, `ghost`, `band`).

## Geometry and export

- **Procedural, from `params/`.** Every part is generated by `blender/scripts/build_units.py`; there are no hand-made sources.
- **One unit, one `.glb`,** with one of each part (design/decisions/0001), built in the machine frame so the ghosted whole machine (`assets/context.glb`) holds them where they stand. The cards are made by the page, from the learner's chain.
- **Export:** glTF 2.0 binary, modifiers applied, no cameras or lights, the rest pose only: runtime code drives every part from the simulation. No baked animation.
- **Budgets:** each unit under 10 k triangles, the ghosted machine under 10 k, all `.glb` files together under 3 MB (checked by J3-9 and J4-4).

## Developer pages (one per milestone)

- Every milestone ships a **permanent** developer page in `dev/NN-name/`, listed in `dev/index.html`. It is how the milestone is verified by hand. The developer pages are prototypes: the site's main page, `index.html`, is the main app ([design/public-app.md](../design/public-app.md)), and the prototype learner page moves into `dev/03-learner/` (in M5). A milestone that builds part of the main app checks it on `index.html` and its `?selftest`; its developer page may simply link there.
- Pages are never deleted when the next milestone arrives. They stay working and act as **live regression tests** in the browser for shared code.
- Every page has a visible **Reset machine** control.
- **Step ▸ and ◂ Step** turn the loom to the next (or previous) of the six moments of a pick, each the moment a visible change has just completed: hooks taken, shed open, shuttle across, beaten up, shed closed, next card pressed. After each step the status line says what just happened. Stepping back unweaves exactly.
- Every page has a **`?selftest`** mode: it runs the milestone's acceptance checks in the page, shows a tick or a cross for each, and publishes `window.__selftest = { done, passed, failed, results }`.
- They run from any static web server at the repository root. Nothing is built.

## Testing

| Layer | Question | Where it is tested | Runs in |
|---|---|---|---|
| 1. Logic | Do the chain, the tie-up, the cycle, the cloth, the links, the store and the languages behave? | `tests/sim/*.test.js`, `tests/app/*.test.js`, `tests/l10n.test.js` | `pnpm test` |
| 2. The 2D drawings | Does each drawing show what the simulation says, and do its parts touch and clear where they should? | `tests/accept/m0`–`m2` (checks in `js/accept/`, measured on the layouts the views draw) | `pnpm test` |
| 3. The 3D models | Do the real 3D parts, posed as the browser poses them, match the 2D section and each other? | `tests/accept/m3`, `m4` (acceptance tests on the `.glb`) | `pnpm test` |
| 4. What is seen | Labels readable and clear of the drawing, the cloth steady, the components in their slots, every language, the pages' own behaviour | The pages' `?selftest` (V-1 to V-3, J2-7 to J2-9, J4-6 to J4-9, G-5, F-3, F-6), and by hand | the browser, or headless: `pnpm selftest` |

### Rules

- **`pnpm test` runs layers 1–3** without a browser, a GPU or Blender. The 3D tests load `assets/*.glb` in Node with three.js (`GLTFLoader.parse`) and measure anchors; no rendering.
- **Tests pose the model through the same code as the page** (`js/sim/`, `js/view2d/`, `js/scene/units.js`). Never re-implement the posing in a test.
- **Each milestone has an acceptance spec**: a numbered list of checkable statements in its design notes (`design/m1-notes.md`, …). Each maps to one test and one `?selftest` check.
- **Three kinds of check:** *readout* (what is drawn or modelled equals the simulation), *contact* (parts that drive each other touch while they act), *clearance* (parts that must not touch keep apart).
- **Tolerances are explicit constants** with a comment saying why (positions 0.01 mm, clearance 0.5 mm).
- **The `.glb` files are in Git LFS.** Run `git lfs pull` after cloning, or the 3D tests fail with "not a glTF binary". If `params/` change, run `pnpm build:model` and commit the new `.glb` with them.
- **CI** (`.github/workflows/test.yml`) runs the reference check, the REUSE lint, the typecheck and `pnpm test` on every push and pull request.

## Code

- **Plain JavaScript ES modules with JSDoc types,** checked strictly by `pnpm typecheck` (`checkJs`, `strict`), run by the browser as written: **no build step**. three.js is vendored in `vendor/` by `tools/vendor.mjs` and reached through each page's import map; Node and the type check use the same version from `node_modules`, and a test fails while the two differ. Tests use Node's own runner (`node --test`).
- `js/sim/` and `js/view2d/` never import three.js; `js/scene/` does.
- **Where code goes:** `js/sim/` the machine, the picture reader, the trace and the links (no DOM, no three.js); `js/view2d/` the 2D drawings; `js/scene/` three.js; `js/teach/` the tutorial and the part names as data (no DOM); `js/game/` the games' logic; `js/app/` the main app (the store, the layout, the workspaces, the tutorial player); `js/ui/` its components ([ui-design.md](ui-design.md), P10); `js/l10n/` the texts, one file per language.
- **Every text a reader sees is a message key** in `js/l10n/en.js`, translated in each locale's file (the ten languages of the sibling project); a test fails while a locale lacks a key or changes a `{placeholder}`.
- **No colour literal in a view:** the 2D drawings, the cloth and the 3D materials take their colours from the theme's tokens ([ui-design.md](ui-design.md), *Theme*).
- **The font and the icons are vendored** like three.js (`pnpm vendor`): Roboto Flex in `vendor/roboto-flex/`, the Material Symbols the page uses written into one module of SVG paths.
- **Caching:** every file a page loads carries `?v=<version>` (`tools/stamp.mjs`, run by `pnpm version` or `pnpm stamp`), through the import map for modules; models take the version from their module's URL. A test fails while a page is out of date.
- **Blender scripts** are Python for Blender's bundled interpreter, run headless (`pnpm build:model`).
- Generated files are never edited by hand: change the script or the params and rebuild.

Writing types in JSDoc:

| TypeScript | JavaScript with JSDoc |
|---|---|
| `function f(a: number): string` | `/** @param {number} a @returns {string} */ function f(a)` |
| `let xs: T[] = []` | `/** @type {T[]} */ let xs = [];` |
| `type P = { a: number; b?: string }` | `/** @typedef {object} P @property {number} a @property {string} [b] */` |
| `import type { T } from "./m"` | `/** @import { T } from "./m.js" */` |
| `x as T`, `x!` | `/** @type {T} */ (x)` (the parentheses are required) |
| `class Rig<K extends string>` | `/** @template {string} K */ class Rig` |
| `import data from "./x.json"` | `import data from "./x.json" with { type: "json" };` |

Pitfalls: URLs relative to the page, never `/…` (GitHub Pages serves the site under `/<repo>/`); every bare import (`"three"`, `"three/addons/…"`) must be in the import map (the stamp test checks it); pages need a web server, since browsers run no module from `file://`.

## References

The repository is public. Nothing in it may point anywhere a reader cannot follow: no private repositories or package scopes, no absolute paths on a developer's machine (`/Users/…`, `/home/…`, `C:\Users\…`), and no relative link, in Markdown or HTML, that leaves the repository or points at nothing. `pnpm check:refs` (`tools/check-refs.mjs`) checks every tracked file, and CI runs it.
